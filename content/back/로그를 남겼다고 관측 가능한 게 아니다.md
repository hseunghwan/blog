운영 중인 SaaS(NestJS 백엔드 + 프론트엔드 + 큐 워커 구성)의 로깅을 전수 조사할 일이 있었다. 결론을 먼저 말하면 — 잘 된 곳은 아주 잘 돼 있었고, 그 외 대부분의 실패·보안·운영 이벤트는 콘솔과 텔레메트리로만 흘러가 **제품 안에서 "무엇이 왜 실패했나"를 질의할 수 없었다.** 그리고 존재하는 로그들은 하나같이 보존 정책 없이 무기한 쌓이고 있었다.

## 먼저 범위를 잘랐다

"로깅"은 범위를 안 자르면 조사가 안 끝난다. 이번 조사는 **DB에 행으로 적재되어 사용자 화면에 노출되는 기록**으로 한정했다. 애플리케이션 디버그 로그(`console.log`, 프레임워크 Logger)와 OpenTelemetry 기반 트레이스·메트릭은 제외.

이 구분엔 이유가 있다. **OTel은 "개발자의 디버깅 흐름"이고, DB 로그는 "제품이 사용자에게 제공하는 관측성"이다.** 전자는 외부 컬렉터가 있어야 동작하고 제품 안에서 질의할 수 없다. 후자는 사용자가 자기 작업의 실패를 스스로 진단하는 기능이다. 둘은 대체재가 아니라 보완재고, 이걸 섞어 생각하면 "OTel 있으니 로깅 충분하다"는 착시가 생긴다.

## 인벤토리: 7종, 목적은 4가지

조사해보니 사용자 대상 기록은 7종이었고, 전부 같은 3단 구조를 공유했다: DB 테이블에 적재 → REST로 조회 → 화면에 타임라인/테이블로 표시.

| 목적 분류 | 해당 기록 |
|---|---|
| 책임 추적성 | 문서 검수 이력(누가 언제 승인/반려, 사유 포함), 멤버십·초대 기록 |
| 회계 투명성·분쟁 대비 | 크레딧 변동 내역(어떤 작업에서 얼마 차감됐는지) |
| 사용자 자가 진단 | 웹훅 발송 이력(재시도 횟수·HTTP 응답), 수집 작업 이력(파일별 성공/실패/스킵 사유) |
| 상태 가시성 | 비동기 작업 진행률(소켓), 스케줄 소스의 마지막/다음 실행 시각 |

목적을 분류해보는 것 자체가 수확이었다. "로그"라고 뭉뚱그리던 것들이 사실 감사 로그(검수·크레딧), 운영 로그(웹훅·수집), 상태 표시(진행률)로 성격이 갈리고, 성격이 다르면 보존·권한·설계 요건도 달라야 한다.

## 발견 1. 모범 패턴은 이미 코드베이스 안에 있었다

수집 작업 이력이 교과서였다. 갖춘 것: **상태 enum + 성공/실패/스킵 카운트 + 건별 reasonCode/reason + 시작·완료 타임스탬프 + 조회 API + 실시간 소켓 갱신.** 사용자가 "1000개 중 3개가 왜 스킵됐나"를 화면에서 건별 사유까지 내려가 확인할 수 있다.

여기서 얻은 규칙: **새 로그가 필요하면 새 구조를 발명하지 말고 이 패턴을 복제하라.** 잘 만들어진 로그 하나가 코드베이스 안에 있으면, 그게 곧 로깅 표준 문서다.

## 발견 2. 보존 정책이 존재하지 않는다

전 테이블을 확인한 결과 — **로그 전용 보존(retention)·만료(TTL)·주기 정리(prune) 정책이 하나도 없다.** 삭제 경로는 세 가지뿐이었다:

1. 부모 레코드 cascade 삭제 (프로젝트를 지우면 딸린 이력도 삭제)
2. 사용자 계정 하드삭제 (탈퇴 후 보존 기간이 지나면 크론이 정리 — 이때 연결 로그가 cascade로 따라감)
3. 수집 소스의 사용자 주도 soft-delete (이력은 남김)

즉 로그를 **나이 기준으로** 지우는 잡은 없고, 전부 사실상 감사 등급 무기한 보존이다. 아무도 그렇게 설계하기로 결정한 적이 없는데 그렇게 되어 있다 — 보존 정책은 정하지 않으면 "무기한"이 기본값이기 때문이다.

문제는 무기한이 공짜가 아니라는 것. 크레딧 내역엔 과금 데이터가, 웹훅 이력엔 외부 응답 본문이 들어 있다. 개인정보 보존 규정과 데이터 증가량 관점에서 "정하지 않은 정책"이 그대로 리스크가 된다. 만료된 초대 레코드가 상태만 EXPIRED로 바뀌고 행은 영구히 남아 누적되는 것도 같은 부류다.

그래서 조사 보고서에 이렇게만 쓰면 안 닫힌다 — "그래서 얼마나 보관할 것인가"를 제안해야 한다. 성격 분류에서 도출한 권장안:

| 기록 성격 | 예시 | 권장 보존 | 근거 |
|---|---|---|---|
| 감사 로그 (행위·금전) | 검수 이력, 크레딧 내역 | 장기 (수년, 규정 따름) | 분쟁·컴플라이언스. 지우면 안 되는 쪽 |
| 운영 로그 (작업 결과) | 수집 작업·아이템 이력 | 중기 (90일~1년) | 자가 진단 용도는 시간이 지나면 소멸 |
| 발송 로그 (외부 응답 포함) | 웹훅 발송 이력 | 단기 (30~90일), 응답 본문은 더 짧게 | 외부 응답 본문은 개인정보 유입 경로 |
| 상태 표시 | 진행률, 실행 시각 | 최신 상태만 (이력 불필요) | 현재값 덮어쓰기로 충분 |
| 만료 레코드 | EXPIRED 초대 | 만료 후 30일 정리 | 남겨둘 이유가 없다 |

숫자 자체보다 중요한 건 **새 로그를 추가하는 시점에 보존 정책을 함께 설계하는 것**이다. 나중에 붙이려면 "이미 쌓인 것을 지워도 되는가"라는 훨씬 어려운 질문이 따라온다.

## 갭 분석: 어디에 로그가 없는가

인벤토리의 짝으로 공백도 조사했다. 가장 큰 발견은 **레이어 구분**이었다.

이 시스템은 문서 처리를 외부 워크플로 엔진에 위임하고, 엔진이 실행 상세(노드별 I/O·에러·소요시간)를 자기 DB에 trace로 남긴다. 그래서 "실행 로그는 있다"고 생각하기 쉬운데 — **trace는 잡이 엔진에 도달한 뒤에만 생긴다.** 큐/워커 오케스트레이션 레벨에서 잡이 stalled되거나 재시도를 소진하고 죽으면 trace 자체가 만들어지지 않고, 워커의 실패 이벤트 핸들러는 콘솔에만 찍는다. **가장 큰 공백은 로그가 "없는 곳"이 아니라, 로그 계층이 커버하지 못하는 "도달 전" 구간이었다.**

부끄러운 정정도 하나 남긴다. 초안에는 "실행 결과가 사용자에게 노출되지 않는다"고 썼는데, 다시 확인하니 틀렸다 — 상태 배지를 클릭하면 trace 다이얼로그가 뜨고 있었다(관리자 전용). 조사 보고서에서 "없다"는 "찾지 못했다"일 수 있다. 반증을 만나면 결론이 아니라 문서를 고치고, 고쳤다는 사실도 남겼다. 정정 후 진짜 갭은 "노출 자체"가 아니라 ① 일반 멤버 가시성 ② 외부 엔진 의존(엔진 장애·trace 삭제 시 조회 불가) ③ 자체 DB에 실행 요약 사본이 없어 단독 집계 불가 — 로 재정의됐다.

그 외 공백 중 시급한 것 둘:

- **RBAC·인증 감사 로그 전무.** 마침 RBAC 도입 작업 중이었는데, 역할·권한 변경이 in-place 덮어쓰기라 "누가 언제 무엇을 바꿨나"가 어디에도 안 남는다. 감사 로그는 소급 생성이 불가능하므로 도입과 동시에 넣어야 한다.
- **크론 실행 이력 없음.** 정리 잡이 언제 돌았고 몇 건을 지웠는지 질의할 수 없다 — 보존 정책을 만들어도 그 집행을 관측할 수 없다는 뜻이다.

## 로그를 만들기 전에 정해야 하는 경계 두 가지

권고를 우선순위로 줄 세우다 보니, 개별 로그 구현보다 먼저 내려야 하는 결정이 두 개 드러났다.

**경계 1 — source-of-truth를 어느 저장소에 둘 것인가.** 실행 trace가 외부 엔진 DB에 있고 우리는 run id로 참조만 하는 현 구조를 유지할지(중복 없음, 대신 엔진 가용성에 종속), 실행 요약(상태·소요·에러 요지)만 자체 테이블에 복제할지(단독 질의·권한 제어 가능, 대신 동기화 책임). 이건 테이블 설계가 아니라 **레포 경계 결정**이라 제일 먼저다.

**경계 2 — 도메인 결과 vs 행위 이벤트.** 도메인 작업 결과(변환·수집·발송)는 전용 테이블로 모범 패턴을 복제하고, 행위·보안 이벤트(로그인, 권한 변경, API 키 사용)는 단일 감사 로그(actor, action, target, metadata, traceId, createdAt)로 통합한다. 이 경계를 안 정하고 필요할 때마다 테이블을 만들면 파편화가 반복되고, **나중에 합치는 마이그레이션 비용이 처음에 정하는 비용보다 훨씬 크다.**

## 코다: 관측의 공백은 인프라에도 있었다

조사 며칠 뒤 실제 다운타임이 났다. 원인은 노드 이미지 버전을 latest로 걸어둔 탓 — 자동 업데이트가 구버전 이미지를 쓰던 노드들을 내렸고, 그 위의 워크플로 엔진 파드가 함께 내려갔다가 k8s가 다시 띄울 때까지 다운타임이 생겼다. 이중화된 본 서비스는 버텼고 단일 구성이던 엔진만 죽었다.

이 사건이 위의 "경계 1"을 실물로 증명했다. 실행 trace의 source-of-truth가 그 엔진 안에 있으므로, **엔진이 죽는 순간 실행 이력의 조회 가능성도 함께 죽는다.** 관측 데이터를 관측 대상과 같은 바구니에 두면, 정작 필요한 순간에 둘이 같이 사라진다.

## 남긴 규칙

1. **로그의 성격(감사/운영/상태)을 먼저 분류하라.** 보존·권한·설계 요건이 성격에서 나온다.
2. **보존 정책은 정하지 않으면 "무기한"이 기본값이다.** 새 로그와 보존 정책은 한 세트로 설계한다.
3. **로그 계층의 커버리지를 그려라.** 공백은 로그가 없는 모듈이 아니라, 어떤 계층도 커버하지 않는 구간(큐→엔진 도달 전)에 있었다.
4. **테이블을 만들기 전에 경계를 정하라.** source-of-truth의 위치, 도메인 결과와 행위 이벤트의 분리 — 나중에 고치면 마이그레이션이고, 먼저 정하면 컨벤션이다.
